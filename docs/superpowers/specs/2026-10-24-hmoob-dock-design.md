# 轻量 Docker 部署与监控平台设计

- 日期：2026-10-24
- 项目目录：hmoob-dock
- 状态：整合设计已获用户最终批准，进入实施规划。
- 本文范围：产品与架构设计，不包含实现代码或实施计划。
- 参考：[Portainer 官方架构说明](https://docs.portainer.io/start/architecture)。参考其控制端与 Agent 分工，不依赖 Portainer，也不复制其完整产品范围。

## 1. 产品定位与已确认决策

面向单管理员、单机 Docker 和小规模多节点 Docker Swarm 环境，提供轻量的 Web 部署与监控平台。核心体验是在应用页面编辑 YAML，点击“保存并部署”，随后查看部署过程与实际运行结果。

最初的单机范围已在需求确认中扩大为“单机 Compose + 多节点 Swarm”；不能将首版描述为只支持单机监控。

| 事项 | 已确认方案 |
| --- | --- |
| 部署位置 | 控制端独立部署，通过远端 Agent 管理目标服务器 |
| 连接方式 | 每个节点部署一个 Agent，Agent 主动连接控制端 |
| 编排支持 | 单机 Docker Compose v2、多节点 Swarm Stack |
| 监控能力 | 实时状态、资源指标、最近 24 小时历史曲线、按需实时日志 |
| 告警能力 | 容器异常退出、Agent 失联、资源持续超限；站内告警与通用 Webhook |
| 用户权限 | 单管理员，不引入多用户、角色权限或多租户 |
| 技术路线 | Go 控制端、Go Agent、Vue 3 + TypeScript 前端、SQLite |
| 外部依赖 | 不要求外部数据库、Redis、消息队列、Prometheus 或 Alertmanager |
| 管理界面 | 概览、站点管理、服务管理、节点管理、告警管理、系统设置六个主要入口 |

## 2. 首版范围

### 2.1 包含的能力

- 接入独立 Docker 主机和一个多节点 Swarm 集群，统一查看所接入节点与容器。
- 新建应用、导入原始 YAML，并明确指定 Compose 或 Swarm 模式。
- 编辑 YAML 和应用环境变量，校验后保存版本并触发异步部署。
- 查看部署输出、应用运行状态、容器日志、历史版本，选择历史版本重新部署。
- 查看 Swarm 节点、服务、期望副本、实际副本及任务状态。
- 收集 CPU、内存、网络和块设备 I/O 指标，查看最近 24 小时趋势。
- 配置告警规则、查看告警事件并通过通用 Webhook 接收异常与恢复通知。
- 初始化管理员、登录退出、修改密码、注册或撤销 Agent。

### 2.2 明确不包含的能力

- Kubernetes、多集群治理、团队协作、多租户和细粒度角色权限。
- 自动安装 Docker、初始化 Swarm、加入或移除 Swarm 节点，以及宿主机自动扩容。
- 上传源码或通过 YAML 中的 `build` 构建镜像；首版部署现成镜像。
- 镜像仓库管理界面、镜像构建流水线或仓库凭据自动分发。私有镜像需要提前配置可用的拉取凭据。
- 任意远程 Shell、宿主机文件管理器、业务数据备份与恢复。
- 长期集中存储容器业务日志、自动修复故障、定时追踪镜像标签更新。
- 自动更新控制端和 Agent 自身。
- 将已有容器自动反向转换为可完整还原原始行为的 Compose 或 Stack YAML。

首版的真实集成验收基线为一个 Compose 环境，以及由一个 Manager 和两个 Worker 组成的 Swarm 环境；不以未经测试的大规模节点或容器数量作为性能承诺。

## 3. 总体架构

### 3.1 组件与职责

| 组件 | 职责 | 依赖与边界 |
| --- | --- | --- |
| Web 前端 | 登录、应用编辑、部署反馈、状态曲线和告警交互 | 仅访问控制端，不直接连接 Agent 或 Docker |
| 控制端 | 管理员认证、应用与版本管理、持久化部署任务、Agent 会话、指标聚合、告警计算和通知 | 单实例 Go 服务，使用 SQLite 和独立主密钥 |
| Agent | 连接本机 Docker，执行受支持的部署操作，采集状态和指标，按需传输日志 | 每节点一个，包含 Docker CLI 与 Compose v2，访问本机 Docker socket |
| SQLite | 保存配置、任务、指标聚合、告警和审计数据 | 控制端本地持久化卷；不作为多个控制端实例共享的数据库 |

控制端容器同时提供前端静态资源和后端接口，无需单独部署前端服务器。Agent 不承载管理页面，不对公网开放 Docker API 或 Agent 入站接口。

### 3.2 通信与数据方向

1. 浏览器通过 HTTPS 访问控制端，提交配置或订阅实时结果。
2. Agent 主动通过经过证书校验的 WSS 长连接接入控制端；部署命令、回执和监控消息通过该连接传输。
3. 控制端把部署任务发给目标 Agent，Agent 调用本机 Docker API 或固定的 Docker CLI 子命令。
4. Agent 返回任务进度、执行输出和本机状态；控制端持久化必要记录并转发页面订阅。
5. 控制端聚合监控数据、计算告警，并向管理员配置的 Webhook 发送通知。

生产部署必须具备有效的 TLS 终止点，可由控制端自身或受信任的反向代理提供；Agent 不提供跳过证书校验的生产接入方式。反向代理需支持长连接。镜像拉取和 Webhook 通知仍需要各自的目标网络可达性。

### 3.3 Docker 与 Swarm 归属

- 一个 Docker 主机对应一个节点身份。节点身份绑定管理员确认的接入记录，不能只凭上报名称替换已有节点。
- Swarm 集群、节点 ID、节点角色来自 Docker 的实际信息，与控制端保存的接入关系核对。
- Compose 应用绑定指定主机，即使该主机同时加入了 Swarm，也仍按本机 Compose 项目处理。
- Swarm 应用绑定集群，不永久绑定某个 Manager。仅把新的 Stack 操作交给已接入、可达且具备 Manager 权限的节点。
- Manager 提供集群服务与任务信息；各节点 Agent 提供本机容器指标与日志。只有 Manager 接入时，不能宣称拥有全部 Worker 的实时监控数据。
- 控制端默认不挂载自身宿主机的 Docker socket，避免无意中取得对控制端宿主机的管理权限。

## 4. 应用模型与 YAML 部署

### 4.1 应用是核心管理单位

一个应用对应一个 Compose 项目或 Swarm Stack，包含名称、模式、目标环境、配置版本、部署任务和运行状态。

创建时确定模式、目标环境和资源命名空间。首版不支持把已有应用直接从 Compose 转换为 Swarm，或原地切换目标环境。项目名或 Stack 名在目标环境内唯一；导入时必须确认资源归属，不能覆盖同名但尚未接管的服务。

执行命令时使用应用绑定的明确项目名或 Stack 名；YAML 中的名称或客户端提交的路径不能改变已绑定的操作目标。

应用页面区分：

- 当前正在编辑但尚未部署的内容。
- 最近一次提交部署的不可变配置版本。
- 最近一次确认部署成功的版本。
- Docker 当前观测到的实际状态。

这些状态不能合并成一个“已保存即已生效”的标记。页面编辑器可保留未提交的修改，但首版不提供独立的服务器端草稿管理功能。

### 4.2 保存并部署流程

1. 管理员编辑 YAML 和应用变量，点击“保存并部署”。
2. 控制端检查语法、配置大小、模式兼容性、变量完整性及目标归属；基础校验失败时返回明确的字段或行级错误，不修改运行服务。
3. 如果配置移除了已有服务，先展示影响并要求确认；未确认则不提交本次部署。首版没有删除数据卷的操作。
4. 控制端在同一持久化事务中创建不可变配置版本和部署任务，然后由后台调度任务。
5. Agent 接收任务，持久化任务标识，校验本地依赖、工作路径和 Docker 配置。此处校验失败时保留失败记录，不执行部署。
6. Agent 准备配置和所需镜像，执行 Compose 更新或 Swarm Stack 更新，并持续回传进度。
7. 控制端继续检查实际容器或服务任务，最后记录成功、失败或状态待确认。

一次保存只触发一个明确的配置版本部署，不自动跟随此后编辑器中的变化。请求必须携带幂等标识和编辑基准版本，重复点击不产生重复任务，过期页面不能静默覆盖更新后的配置。

### 4.3 Compose 与 Swarm 的差异

| 事项 | Compose | Swarm |
| --- | --- | --- |
| 执行位置 | 应用绑定主机上的 Agent | 目标集群的可用 Manager Agent |
| 执行机制 | Docker Compose v2 的配置校验和 `up` 更新流程 | Docker Stack 的配置校验和 `deploy` 流程 |
| 更新行为 | 重建需要变更的容器，不先整体停止应用 | 按服务的更新策略滚动替换任务 |
| 配置兼容性 | 按支持的 Compose 规范校验 | 按实际 Stack 支持的 Compose 文件语义校验 |
| 就绪判断 | 检查目标容器状态及已配置的健康检查 | 检查服务期望状态、任务、更新状态及健康检查 |

不能认为 Stack 支持全部 Compose 特性。`build`、不支持的编排字段和不适用于目标模式的依赖关系必须明确报错或警告；会改变部署含义的不支持字段必须阻止部署，不能依赖 CLI 静默忽略。

应用变量只来自应用显式配置，不从控制端或 Agent 的进程环境中隐式获取。Swarm 不依赖自动读取 `.env` 的假设，必须显式处理受支持的变量插值。变量插值与传入容器的环境变量是不同概念，界面和校验需区分。

### 4.4 工作目录、挂载与镜像

- Agent 使用持久化的应用工作目录保存执行所需配置，目录权限限制为 Agent 所需的最小范围。
- 容器化 Agent 的应用工作目录必须以相同绝对路径映射到宿主机，确保 Compose 解析后的相对 bind mount 路径对宿主机 Docker 有效。
- YAML 引用的宿主机目录、外部配置文件和外部 Docker 资源需提前准备；不通过本平台上传任意文件。
- 本地配置文件如 `env_file`、`configs`、`secrets` 的读取发生在执行命令的 Agent 文件系统中，不能误认为挂载 Docker socket 后即可读取所有宿主机文件；需按应用目录约定预先准备。
- Swarm 中 bind mount 所依赖的路径必须存在于可能调度该服务的节点上。Manager 本地检查不能替代 Worker 检查，无法核实的条件必须展示给管理员。
- 使用现成镜像，部署时执行相应模式下的镜像拉取或解析流程；准备阶段发现失败时不继续主动执行更新。Swarm Worker 上的后续镜像拉取失败仍可能造成部分更新。
- 保存同一可变镜像标签后重新部署，可能使用标签指向的新镜像；平台不在未保存部署时自动更新镜像。
- 历史 YAML 重新部署不保证拿到过去的镜像内容；需要镜像可复现时应使用 digest 固定镜像版本。
- 移除服务需经确认后执行应用范围内的清理，不执行全局 prune，不删除持久化数据卷。

### 4.5 成功、失败与历史重部署

命令返回零不等于业务服务可用：

- 对长期运行容器，检查运行状态；存在健康检查时检查健康结果。
- 没有健康检查时，只能声明“已运行”，不能声明业务健康。
- 对 Compose 一次性任务，结合配置语义和退出码判断，不把正常完成的任务当成异常退出。
- 对 Swarm，检查目标副本或全局服务的目标任务、更新状态与失败原因。

Compose 更新不是事务，失败可能已经改变部分容器。Swarm 按 YAML 中配置的更新与回滚策略工作，平台不叠加不可预测的自动回滚。

历史版本操作统一称为“重新部署该版本”。它创建新部署任务，不回滚数据库、数据卷或外部系统。若 Swarm 自动回滚，页面必须展示回滚结果，不能将新配置标成已成功运行。

已有但未经平台接管的容器和服务可查看状态、指标和日志；要编辑部署必须导入原始配置并确认资源归属。平台不自动还原完整 YAML，也不在后台自动覆盖用户在平台外的变更；管理员再次提交部署时，仍以本次提交的 YAML 为目标配置，预检中发现的外部变更必须提示。

## 5. 任务可靠性与错误处理

### 5.1 持久化任务和互斥

控制端使用 SQLite 保存部署任务，不引入外部消息队列。同一应用同时只能有一个未结束的部署任务；不同应用可在受控并发范围内执行。

任务状态包括：排队、预检、执行中、验证中、成功、失败、状态待确认。前端订阅连接是否存在不影响任务运行。

Agent 保存最低限度的任务日志账本，包括任务 ID、应用 ID、配置版本和执行状态。它不是完全无状态组件，重启后不能因为丢失内存记录而自动重跑任务。

### 5.2 断线、重启与 Manager 切换

- 控制端重启后从数据库恢复任务视图，与 Agent 核对已接收、正在执行和已完成的任务。
- Agent 断线后按退避策略自动重连；控制端不把通信超时直接等同于部署失败。
- 断线期间可能仍有 Docker 操作在执行，未确认前不重复下发，也不向其他 Manager 自动重试同一任务。
- Agent 或执行进程状态不明时，结合账本和 Docker 实际状态核对；无法证明结果时保持“状态待确认”，而不是猜测成功。
- 同一应用的后续任务保持阻塞，直到核对完成；需要人工解除时，要求管理员先确认原执行端不再继续操作。
- 新的 Swarm 部署可使用其他可用 Manager，但已有结果不明的任务不能凭 Manager 切换绕过互斥。

首版不宣称实现分布式“严格只执行一次”；通过持久化、幂等接收、互斥和不盲目重试降低重复执行风险。

### 5.3 输出、超时与错误分类

部署命令必须具有受控的执行期限和输出上限；健康等待也有明确期限。超时需要区分“已确认操作失败”和“仍可能在 Docker 中继续执行”。

界面分别展示配置错误、目标不可达、镜像准备失败、Docker 执行失败、服务未就绪和结果待确认。给出简洁结论与可展开的相关日志，不以内部连接组件报错代替业务状态。

用户主动停止、部署中的预期替换与真正的运行故障应在事件关联中区分，但不能因为应用处于部署中就屏蔽所有异常。

## 6. 监控与日志

### 6.1 采集与展示

- 默认每 10 秒采集一次容器 CPU、内存、网络和块设备 I/O 指标。
- 展示容器运行状态、健康检查状态和资源限制。CPU 按每核 100% 的口径展示，多核使用可超过 100%；内存采用 Docker API 上报的当前使用字节数，单独展示容器限制；网络和 I/O 速率使用字节/秒。
- 计数器重置、容器重建和采样时间变化必须参与速率计算，不能显示负速率或把新容器续接为旧容器计数。
- 节点展示连接状态和 Docker 信息；Swarm 展示节点角色、可用性、服务与任务状态。
- 首版资源曲线以容器指标为准，不将 Agent 容器自身的 CPU、内存数据冒充为宿主机完整指标。
- 每个数据点携带采集时间和来源身份，控制端校验时钟偏差；过期数据不得刷新节点实时状态。

### 6.2 历史数据与容量

实时数据用于页面更新及告警判断，按一分钟聚合保存平均值和峰值，历史保留最近 24 小时。不把实时原始采样全部永久写入 SQLite。

断线时展示缺口或过期标记，不补零。Agent 不承担历史指标补传队列，控制端不可用期间的历史数据允许缺失。

SQLite 使用适合单实例读写的并发模式和批量写入，按时间批量清理历史数据。指标写入受限时不得无限积压内存，也不得阻塞部署任务持久化；被丢弃的样本应反映为数据缺失。

### 6.3 日志

容器业务日志按需拉取最近一段并实时跟随，关闭页面订阅后停止对应传输；不把所有容器日志永久存入控制端。

实时日志和部署输出都需要缓冲、速率和体积上限。输出按纯文本渲染，防止日志或 YAML 中的内容变成浏览器可执行代码。部署输出达到保存上限时明确显示截断提示。

Docker 日志驱动不支持读取、容器已删除或节点不可达时，展示实际原因，不伪造空日志为正常结果。

## 7. 告警

### 7.1 规则与语义

| 规则 | 触发依据 | 降噪与恢复 |
| --- | --- | --- |
| 容器异常退出 | 意外停止、失败退出，或服务任务异常终止 | 关联部署、可确认的人工停止和一次性任务语义；已确认的正常行为不报警 |
| Agent 失联 | 超过连接心跳容忍时间 | 表示失联，不断言宿主机宕机；恢复连接后产生恢复事件 |
| 资源持续超限 | CPU 或内存等已配置指标连续超过阈值和持续时间 | 阈值、持续时间可配置；缺失数据不视为恢复，也不视为持续超限 |

不能仅凭退出码为零就认定长期运行服务的退出符合预期，也不能可靠推断所有平台外停止操作的意图。无法关联到已知操作时保留异常提示，并允许管理员确认事件；首版不承诺识别所有外部操作意图。

同一规则与同一监控对象的持续异常合并为一个事件；记录首次发生、最近观测和恢复时间。重复采样不产生重复新告警。对 Swarm 用稳定的服务/任务槽位关联事件，避免滚动替换造成无意义的重复通知。

### 7.2 通知与限制

站内告警是权威事件记录。Webhook 发送失败不丢弃站内事件，通过有次数上限的退避重试处理，并显示通知结果。失败通知不能无限堆积或阻塞部署。

Webhook 使用通用 JSON 事件格式，包含事件 ID、环境、对象、规则、状态、发生时间和简洁描述，不附带 YAML、环境变量或接入凭据。下游可使用事件 ID 去重。

首版不包含针对邮件、短信或特定聊天机器人格式的适配器。恢复时发送恢复通知；控制端自身停机期间无法发送告警，Agent 失联也不等于服务器宕机。

## 8. 安全与凭据

### 8.1 管理员与会话

- 首次初始化使用仅部署者可获得的短期初始化凭据设置管理员密码，避免任何先访问页面的人抢先注册。
- 不提供默认账号密码；密码以加盐慢哈希保存。
- 登录接口限制尝试频率；使用具有安全属性的会话 Cookie，并对修改操作进行 CSRF 防护。
- 修改密码后撤销已有登录会话。所有配置、日志和部署接口均验证会话和目标归属。
- 实时连接同样验证身份，不通过 URL 查询参数携带长期凭据。

### 8.2 Agent 接入

管理员创建短期一次性令牌，在目标节点启动 Agent 完成注册。注册成功后签发独立节点凭据，后续不再使用接入令牌。

控制端只保存令牌与节点凭据的不可逆校验值。Agent 将自身凭据保存在权限受限的持久化文件中，通过受验证的 TLS 连接认证；不得在日志或安装历史展示可复用的完整凭据。

撤销节点凭据会关闭连接并阻止再次认证，但不会停止该主机正在运行的业务容器。

### 8.3 Docker 权限边界

Agent 使用固定命令与结构化参数，不把 YAML、路径或用户输入拼接成 Shell 命令，不提供通用远程 Shell。

Docker socket 管理权限本质上接近宿主机 root 权限。即使 Agent 不使用特权容器，恶意部署配置仍可能取得宿主机访问能力；不能把这一方案宣称为针对不可信用户的隔离沙箱。

平台只能由可信管理员使用。敏感 bind mount、宿主机命名空间或特权容器配置需要清楚显示影响，不以“有登录”替代权限风险说明。

### 8.4 数据保护与 Webhook

- YAML、应用变量及其他可恢复的敏感配置使用带完整性验证的加密保存；主密钥通过独立的受保护文件提供，不与 SQLite 文件存放在一起。
- 管理员密码、一次性接入令牌和可撤销节点凭据使用不可逆校验值，不使用可恢复加密代替密码哈希。
- 日常操作日志不记录凭据、完整 YAML 或完整环境变量；业务日志本身可能含有敏感内容，不能保证自动识别所有秘密，必须限制访问。
- 临时生成的部署配置和变量文件使用受限权限，日志不得输出配置展开后的全部内容。
- Webhook 仅使用受支持的 HTTP/HTTPS 地址，推荐 HTTPS；控制出站目标、重定向、超时和响应体大小，阻止访问本机、链路本地与云元数据端点。内网通知地址由管理员显式配置。
- 数据备份需同时保管数据库和独立主密钥；缺失密钥时无法恢复加密配置。业务数据卷不属于平台备份范围。

## 9. 数据模型与保留策略

### 9.1 核心记录

| 记录 | 内容 |
| --- | --- |
| 管理员与会话 | 密码校验值、登录会话、初始化状态 |
| 环境与节点 | Docker/Swarm 身份、节点角色、连接状态、凭据校验值 |
| 应用 | 名称、模式、环境绑定、命名空间、当前版本引用 |
| 配置版本 | 不可变 YAML 和变量快照、内容摘要、创建时间 |
| 部署任务 | 幂等标识、配置版本、目标 Agent、状态、时间、受限输出 |
| 指标聚合 | 对象身份、时间桶、平均值、峰值、样本完整性 |
| 告警规则与事件 | 条件、对象、持续状态、触发/恢复时间、通知尝试 |
| 审计事件 | 登录与重要操作、目标、结果、时间，不包含敏感配置正文 |

运行中的容器和服务信息来自 Docker，不把数据库快照当成实时事实。应用配置由平台保存，实际运行状态独立观测；后台采集不会覆盖应用配置，也不会触发自动部署来纠正实际状态。

### 9.2 工程默认值

以下是供整合设计审阅的工程默认值，可在实施时按此实现配置项，不作为新增产品能力：

| 项目 | 默认值或策略 |
| --- | --- |
| 指标采集间隔 | 10 秒 |
| 历史聚合粒度与保留 | 1 分钟，24 小时 |
| Agent 心跳与失联判断 | 10 秒心跳，持续 60 秒未收到有效心跳判定失联 |
| 一次性接入令牌有效期 | 15 分钟，成功使用一次即失效 |
| 单任务已保存输出上限 | 2 MiB，超限截断并提示 |
| 已结束部署、告警和审计记录 | 默认保留 90 天 |
| 配置版本 | 每应用保留最近 50 个；正在执行和最近成功版本不因数量上限删除 |
| Webhook 重试 | 初次失败后最多重试 3 次，采用退避间隔 |
| 资源告警阈值 | 由管理员显式配置，不凭空采用统一生产阈值 |
| 部署执行与就绪等待 | 分别有可配置期限，默认各 10 分钟；超时不等于 Docker 操作已停止 |

配置版本清理必须保护尚被保留的部署记录引用的版本；因此最近 50 个是保留底线而不是违反引用完整性的硬删除上限。未结束或待确认的任务不按普通历史记录自动清理。

| 入口 | 内容 |

“保存并部署”是配置页的主操作；部署中展示进度并禁止再次提交同一应用。失败结果、实际运行状态和配置保存状态分别显示。

## 11. 验证与验收

### 11.1 自动化验证

- 单元测试覆盖配置校验、模式差异、变量处理、幂等请求、版本冲突、状态转换、指标计算、告警去重、保留策略和凭据验证。

- 使用 Agent 协议测试验证重复回执、乱序、断线重连、撤销身份、非法目标以及大小限制。
- 验证命令参数传递、日志纯文本渲染、会话保护和敏感信息不进入平台生成的日志。

### 11.2 真实 Docker 场景

在隔离的测试主机或测试集群执行，不在未授权的现有业务环境试验：

1. 创建 Compose 应用，修改 YAML 后保存部署，验证容器变化与实际状态。
2. 在 Manager + 两个 Worker 的 Swarm 中部署 Stack，修改副本或镜像，观察任务分布与滚动更新。
3. 验证 Compose/Stack 不兼容字段、变量缺失、目录或外部资源缺失、镜像拉取失败等错误。
4. 制造部分更新失败、健康检查失败和 Swarm 自动回滚，确认页面不误报成功。
5. 在部署过程中断开 Agent 连接、重启控制端或 Agent，验证不盲目重复执行，也不错误解除应用互斥；另用具备正常 quorum 的多 Manager 测试环境验证新任务切换和结果不明任务不自动迁移。
6. 验证历史 YAML 重新部署，以及数据卷未被默认删除；明确镜像标签变化和业务数据不回滚的边界。
7. 覆盖异常退出、预期容器替换、失联、持续超限、通知重试、去重与恢复。
8. 验证日志订阅关闭后的资源释放、慢客户端限流、指标缺口、24 小时清理和任务输出截断。
9. 验证未登录访问、初始化保护、节点凭据撤销、会话失效及配置注入边界。

### 11.3 浏览器验证

启动真实开发服务，在浏览器操作登录、接入、应用导入、YAML 编辑部署、日志、曲线和告警流程，检查空状态、错误状态、断线状态、窄屏、页签切换、长文本及控制台异常。

类型检查和模拟页面通过不能替代真实功能验证。如果执行环境缺少 Docker、Swarm 节点或浏览器能力，必须明确列出尚未验证的项目，不将首版标记为已完整验收。

## 13. 范围扩展附录：节点详情与容器操作（2026-11-05 批准）

在首版三阶段完成后，用户批准按交互原型 `docs/prototype/saas-workloads.html` 扩展以下能力。本附录记录其设计边界，与正文冲突时以本附录为准。

### 13.1 节点详情

- 新增一级导航「节点管理」：列表页以 Portainer Environments 式的一行一节点展示连接状态、角色、Docker/系统/Agent 版本、最近上报与站点/容器/运行中数量，行内可撤销接入；节点详情页为 `/nodes/{id}`。
- 节点详情页按 Portainer 环境页组织：紧凑的节点头部与四个读数，下方用「容器 / 服务 / 网络」三个页签直接列出对象。容器表格展示状态、堆栈、镜像、创建时间、IP 与端口；服务页签展示 Swarm 服务（名称、堆栈、镜像、模式、副本、端口、更新时间/状态），独立主机则以容器上的 Compose 标签派生服务；网络页签展示名称、驱动、范围、内部、容器数与创建时间。
- 容器可进入 `/nodes/{id}/containers/{cid}`：展示 ID、镜像、状态/健康、创建与启动时间、IP、端口、挂载、标签、重启次数与退出码，并提供启动/停止/重启/删除（删除仅限未接管容器）、实时日志与资源曲线。
- 接入 Agent 的一次性令牌入口放在节点列表页顶部（「接入节点」），系统设置只保留管理员密码；撤销接入同样在节点行内完成。
- 节点详情展示：连接状态、Swarm 角色、节点 ID、Docker 引擎版本、操作系统/架构、Agent 版本、接入时间、最近上报。这些来自节点最近一次上报（`NodeIdentity` 扩展 `server_version/os_type/architecture`，`Hello` 扩展 `agent_version`），持久化到 nodes 表，断线后仍展示且页面注明「不是实时探测结果」。
- 容器清单按命名空间分组（平台站点容器 / 未接管），未接管的容器（无 Compose project 或 Stack namespace 标签）单独成组并有明确说明。

### 13.2 容器操作

- 支持对单容器执行 start / stop / restart / remove。协议新增 `container.command` / `container.result`，以 `Envelope.RequestID` 关联；控制端 `Hub.Request` 同步等待结果（30 秒），Agent 侧 `opsManager` 有界并发（2）执行并回执操作后的容器状态。
- 操作使用 Docker SDK 的固定方法（`ContainerStart/Stop/Restart/Remove`），不引入 Shell 面；stop 优雅期 10 秒；remove 不删除数据卷与镜像。
- 策略边界：
  - 由平台站点管理的容器（namespace 匹配已注册应用）**拒绝 remove**（`managed_by_application`）——删除属于站点 YAML 的重新部署；
  - 该应用存在未结束部署任务时拒绝 start/stop/restart（`deployment_in_progress`）；
  - 节点断线、撤销、容器不在最近清单时直接拒绝，不发送命令。
- 操作完成写审计（action=`container_op`，detail 含动作/容器/结果）；超时返回 504 并如实说明「操作可能仍在节点上执行」，不声称失败。
- 清单扩展：容器携带创建/启动时间、首个网络 IP、端口与挂载；Swarm 服务携带镜像、发布端口与更新时间；清单新增节点的 Docker 网络。批次中随首批携带网络与 Swarm 事实，控制端合并为一份完整清单。
- Agent 完成操作后立即上报一次清单（不等 10 秒 tick）；页面以 SSE `container` 事件（object_id=节点 ID）驱动刷新，并以 15 秒轮询兜底。
- 不提供执行终端、批量操作、操作历史页面（正文 8.3 的远程 Shell 禁令不变）。

### 13.3 概览重设计

概览页按新版设计重做：Hero 横幅 + 四个可点击读数（站点/服务/容器/健康率）+ 站点服务总览（状态与健康分段）+ 整体运行状态（服务环形图、图例与 24 小时趋势）+ 最近告警；节点清单与接入移至节点管理页。

### 13.4 已知开发环境限制

vite dev 代理（http-proxy）对 HTTPS 上游的 SSE 存在缓冲问题：开发环境下 `container` 事件可能延迟到达，页面依赖 15 秒轮询兜底。生产路径（控制端同源直服前端）不受影响。
